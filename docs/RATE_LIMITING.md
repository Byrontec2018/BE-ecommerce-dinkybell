# Rate Limiting Documentation

Implementation details for endpoint protection against brute force, abuse, and request flooding in BE-Auth-Service.

---

## Overview

The project applies endpoint-level throttling using:
- Resilience4j `@RateLimiter` annotations on auth endpoints
- a custom AOP layer (`CustomRateLimiterAspect`) to enforce Redis-backed counters
- custom key resolution (`RateLimiterKeyConfig`) for user/IP-aware isolation
- Redis storage with fail-open behavior if Redis is temporarily unavailable

This design protects critical auth flows while keeping rate-limiting logic separated from business code.

---

## How It Works

Request flow for annotated endpoints:
1. Controller method is intercepted by `CustomRateLimiterAspect`
2. Limiter name is read from `@RateLimiter(name = "...")`
3. A key is generated by `RateLimiterKeyConfig.resolveKey(...)`
4. `CustomRedisRateLimitService` checks and increments the counter in Redis
5. If limit is exceeded, a `RateLimitExceededException` is thrown

Key properties:
- distributed counters through Redis
- per-operation isolation (`login`, `register`, etc.)
- user-aware limits for authenticated requests
- IP + User-Agent hashed keys for anonymous requests

## Endpoint Coverage

Rate-limited endpoints currently implemented:
- `POST /api/v1/auth/register` (`register`)
- `POST /api/v1/auth/login` (`login`)
- `POST /api/v1/auth/forgot-password` (`resetPassword`)
- `POST /api/v1/auth/reset-password` (`confirmResetPassword`)
- `POST /api/v1/auth/refresh-token` (`refreshToken`)
- `POST /api/v1/auth/revoke-token` (`revokeToken`)
- `POST /api/v1/auth/revoke-other-sessions` (`revokeOtherSessions`)

---

## Current Limits (application.yml)

Configured limits in `resilience4j.ratelimiter.instances`:

- `login`: 3 requests per 300s
- `register`: 2 requests per 600s
- `resetPassword`: 1 request per 900s
- `confirmResetPassword`: 2 requests per 600s
- `refreshToken`: 2 requests per 60s
- `logout`: 5 requests per 300s

Notes:
- `logout` is configured but currently the logout endpoint is not annotated with `@RateLimiter`
- `verifyEmail` and `resendVerificationEmail` configs may exist in properties but are not currently wired to active controller annotations
- `revokeToken` and `revokeOtherSessions` have defaults in the aspect (`5/300s`) unless explicit instance config is added

## Key Generation Strategy

`RateLimiterKeyConfig` builds keys as follows:

- Authenticated requests:
  - `{limiter}:user:{username}`
- Anonymous requests:
  - `{limiter}:ip:{clientIp}:ua:{userAgentHash}`

Examples:
- `login:ip:203.0.113.10:ua:19827364`
- `refreshToken:user:user@example.com`

This reduces cross-user interference and improves abuse attribution.

---

## Redis Behavior

`CustomRedisRateLimitService` uses keys with prefix:
- `rate_limit:{resolved_key}`

Behavior:
- first request creates counter with TTL = window
- subsequent requests increment counter
- request denied when `count >= maxRequests`
- remaining window derived from Redis TTL

Failure mode:
- if Redis errors occur, service logs the error and allows the request (`fail-open`) to avoid hard auth outages

---

## Error Handling

When a limit is exceeded, the service raises `RateLimitExceededException` with:
- limiter name
- retry-after seconds
- max request threshold

Global exception handling maps this into a standardized API error response (HTTP 429).

---

## Security Rationale

Why strict limits matter on auth endpoints:
- `login`: mitigates credential stuffing and brute force
- `register`: reduces mass-account creation abuse
- `forgot-password`: prevents reset email flooding/enumeration pressure
- `reset-password`: protects reset token verification path
- `refresh-token` and revoke endpoints: limits token endpoint abuse and session tampering attempts

---

## Operational Notes

For production tuning:
1. keep Redis highly available to preserve consistent distributed throttling
2. tune per-endpoint limits based on observed traffic patterns
3. monitor 429 rates to detect abuse or overly strict limits
4. avoid excessively high windows on user-facing auth routes
